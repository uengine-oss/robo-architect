# 그래프 권한 서버 이관 — 2026-10-12 조사

현재 설치 앱의 두 계정 프로젝트 격리는 검증됐지만, PC에 관리자 DB 자격이 있으므로
클라이언트 자체 변조까지 막는 AUTH-1 배포 구조는 아직 완성되지 않았다.

## 현재 특권 호출

| 경로 | 사용 특권/비밀 | 이관 대상 |
|---|---|---|
| projects/roles.py ensure_role | CREATE/ALTER ROLE, AUTH_ROLE_SECRET | 서버 사용자 역할 운영 |
| projects/store.py create_project/adopt_graph | og_create_graph, og_grant | 서버 프로젝트 운영 |
| projects/store.py share/unshare/set_analyzer_graph | og_grant/og_revoke | 서버 공유 및 분석 그래프 선택 |
| identity/connection_binding.py resolve_for_request | 쓰기 사용자를 NEO4J_USER/PASSWORD 관리자 자격으로 연결 | 서버가 프로젝트·사용자를 확인한 쓰기 실행 |
| projects/store.py 그래프 복사/권한 회수 | 관리자 Bolt, 권한 함수 | 서버 운영 경로 |
| desktop runtime 컨테이너 analyzer/catalog/fabric | 공유 그래프 사용자·비밀번호 | 서비스별 범위 제한 자격 또는 서버 실행 |

## 단순 프로젝트 API 프록시만으로 완료되지 않는 이유

중앙 계정 API는 CREATEROLE이 없는 제한 역할로 시작한다. 현재 프로젝트 저장소를 그대로
include_router하면 역할 생성에서 실패한다. 별도의 서버 전용 특권 운영 경계가 필요하다.
또한 프로젝트 API만 이전해도 PC의 ingestion은 새 라벨·뷰 생성에 관리자 자격을 사용한다.
PC에 공용 관리자 비밀번호와 AUTH_ROLE_SECRET을 남기면 다른 계정 역할을 유도하거나
권한 표를 바꾸는 경로가 남는다. 계정 표 ACL만으로 해결되지 않는다.

## 구현 순서와 인수 조건

1. 서버 전용 프로젝트 운영 경계에 최신 계정 승인과 프로젝트 admin 권한 검사를 둔다.
   운영 비밀은 PC에 제공하지 않고, 사용자별 DB 역할 생성 및 공유 변경을 서버에서만 한다.
2. 현재 Ontological 버전에서 범위 제한 역할의 라벨/뷰 생성·ingestion 쓰기를 격리 DB로 확인한다.
   부족한 특권은 범용 SQL·Cypher 관리자 프록시를 만들지 않고 서버 측 프로젝트 고정 실행으로 처리한다.
3. 비동기 ingestion·탐색·승격 및 analyzer/catalog/fabric의 실제 자격을 같은 경계로 전환한다.
   프로젝트는 클라이언트가 보낸 값만 믿지 않고 승인·현재 공유 권한을 확인해 고정한다.
4. 모든 PC/서비스의 실제 자격을 회수한 뒤 공용 관리자 DB 비밀번호와 역할 유도 비밀을 교체한다.
5. 계정 환경변수 변조, 직접 SQL, 역할 전환, 다른 프로젝트 graph 지정, 회수 후 기존 작업/토큰,
   일반 사용자 ingestion 정상 동작을 확인하고 설치본으로 검증한다.

현재 VM과 설치 앱은 사용자 시험용으로 그대로 유지한다. 이 조사는 서버 이관 구현 완료가 아니다.
실제 SWP와 사내망 연결은 현장에서 확인하며, 격리 구현 검증은 여기서 진행 가능하다.

## 후속 구현 — 프로젝트 운영 경계

PC `/api/projects` 경로의 중앙 전달과 중앙 서버 라우터를 구현했다.
계정 승인 확인은 제한 DB 자격, 프로젝트 운영은 서버 전용
`ROBO_PROJECT_OPERATOR_DSN`을 요청별 ContextVar 범위로 사용한다.
동시 요청 간 범위 분리와 예외 후 복원, 승인 거절 시 특권 미사용, 설정 부재 시 503,
실제 격리 DB의 프로젝트 생성·목록 분리·타인 멤버 조회 거절을 검증했다.
기존 graph adopt는 중앙 관리자 전용이며 runtime DDL은 제거했다.
통합 격리 검사 135개 통과. VM 배포·설치본 반영 전이며 위 순서 2~5는 남아 있다.

## 운영 구성 선택과 권한 구분 — 2026-10-12 설명 보완

관리자 역할을 DB에서 읽어 사용자 승인·템플릿 관리 기능을 가르는 변경은 설치본에 반영됐다.
일반 member도 프로젝트 write/admin이면 ingestion을 실행할 수 있다. 앱 admin과 DB 특권 계정은 다르다.
역할 조회 자체 때문에 중앙 중재 서비스가 필수인 것은 아니다.

현재 설치 앱은 graph-db/Bolt 두 개만 서버에 두고 나머지 서비스를 PC에서 실행할 수 있다.
다만 PC가 ingestion용 관리자급 DB 자격을 보유하므로 앱 검사를 우회한 직접 DB 접근까지 차단하지 못한다.
DB 역할 조회는 이 자격의 실제 DB 권한을 줄이지 않는다.

선택 A: DB/Bolt 두 개 유지. 제한 사용자 역할로 자신의 프로젝트의 라벨·스키마 생성과 ingestion을
실행할 수 있도록 DB/그래프 엔진의 권한 경계를 개선·검증한다. 현재 scoped 역할은 새 라벨·스키마
생성에 필요한 권한이 부족하다. 공용 스키마 CREATE나 전역 관리자 GRANT만 주면 프로젝트 격리가
훼손될 수 있으므로 이것만으로 해결했다고 판정하지 않는다.

선택 B: 서버 API가 권한을 중재하고 특권 실행을 맡는다. PC에서 특권 자격을 제거한 뒤에도
중앙 API/실행 서비스는 계속 운영해야 한다. 제거할 때만 잠깐 쓰는 임시 서비스가 아니다.
계정/실행 기능을 반드시 별도 두 컨테이너로 운영할 필요는 없고 통합 배포도 가능하다.

현재 VM의 추가 API 두 개는 B의 시험 구현이다. 앱은 아직 A의 기존 직접 DB 연결을 사용한다.
B를 최종 사내 납품 구성으로 확정한 것으로 간주하지 않는다. 추가 서비스가 필요한 구조 변경을
충분히 설명하기 전에 구현을 진행했으며, 운영 구성 선택을 명확히 한 뒤 후속 전환을 진행한다.
기존 역할 DB 지정 완료를 전체 DB 특권 보호 완료와 혼동하지 않는다.

## 격리 DB 권한 재현 결과 — 2026-10-13

기존 로컬/VM 데이터를 사용하지 않고 `tmpfs` ontological-db 컨테이너에서 실제 제한 역할로
확인했다. `og_grant(role, 'write', graph)`만 적용한 프로젝트 writer는 기존 라벨의 노드 생성도
`og_data.og_id_alloc` 권한 부족으로 실패했고, 새 라벨 생성은 `og_catalog.type` 권한 부족으로
실패했다. ID 할당 테이블 DML을 추가하면 기존 라벨 쓰기는 성공하지만 해결책은 아니다.

더 중요한 반증은 scoped writer가 공용 `og_data.og_node`에 직접 DML 권한을 갖는다는 점이다.
프로젝트 A에만 write를 준 로그인 역할이 `UPDATE og_data.og_node SET id=id`로 프로젝트 A/B의
공용 행을 모두 갱신했다. 반면 다른 프로젝트의 타입 뷰 조회, `public.app_users` 변경,
운영자 역할로 `SET ROLE`은 거부됐다. 즉 함수/API 정상 경로의 프로젝트 검사는 동작하지만,
PC에 이 DB 자격을 전달하면 직접 SQL로 공용 spine을 변조할 수 있어 보안 경계가 되지 않는다.

따라서 현재 엔진에서 선택 A는 단순 GRANT 보강으로 채택할 수 없다. 구현하려면 최소한 공용
spine/allocator의 graph-aware RLS, 신규 타입·속성 DDL을 위한 검증된 SECURITY DEFINER 경계,
직접 SQL 우회 및 revoke 회귀 검사가 추가로 필요하다. 이는 이미 구현한 중앙 중재보다 변경
범위와 위험이 크다. 운영 구성은 선택 B(중앙 authority와 DB central, 특권 자격 서버 한정)를
권고한다. ingestion·분석 서비스는 PC에서 실행하되, 프로젝트 경계를 벗어난 DB 쓰기를 할 수
없는 제한 자격과 서버 중재 경계를 완성해야 한다.
