# Feature Specification: 설치본 런타임 감독과 복구

**Feature Branch**: `enterprise-custom-p` (전용 브랜치를 만들지 않는다 — 기업 커스터마이징 작업은 이 브랜치 하나로 간다)

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "Electron 앱이 모든 서비스를 안정적으로 실행·관리한다. 서비스별 준비 상태를 화면에 드러내고, 실패 시 영향받은 기능과 복구 방법을 보여준다. 앱이 소유한 스택의 종료·재실행·OS 재시작 후 정합성. 설치본과 개발 환경의 graph 설정 계약 일치. 장애 시 재기동과 복구. BPMN 결과의 처리 출처를 기록으로 남긴다."

## 왜 이것인가

`054-docker-managed-electron-distribution` 이 **무엇을 어떻게 묶어 배포하는가**를 정했다.
이 스펙은 그 위에서 **묶인 것이 실제로 돌고 있는지 사람이 알 수 있는가, 안 돌 때
어떻게 되돌아오는가**를 정한다. 지금은 8개 서비스의 생사가 백엔드 상태값 하나로
접혀 있고, 그 하나조차 화면에 그려지는 곳이 없다.

**이 기능의 실패 모드는 "조용히 아무 일도 안 일어난다"가 아니라 "조용히 다른 일이
일어난다"이다.** 기동 중과 고장을 사용자가 구분하지 못하고, 폴백이 성공처럼 보이고,
분석이 설계를 지운다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 지금 무엇이 준비됐고 무엇이 안 됐는지 보인다 (Priority: P1)

사용자가 앱을 처음 실행한다. 이미지 압축 해제와 서비스 기동에 수 분이 걸린다.
그 동안 화면은 **어느 단계에 있는지**를 말하고, 다 끝나면 **어떤 기능이 열렸는지**를
말한다. 한 서비스가 못 뜨면 **그것 때문에 못 쓰는 기능**과 **사용자가 할 수 있는 일**을
같은 자리에서 말한다.

**Why this priority**: 이것이 없으면 나머지 모든 고장이 "앱이 안 켜진다" 한 문장으로
합쳐진다. 진단도 복구도 시작할 수 없다.

**Independent Test**: 서비스 하나를 일부러 못 뜨게 만든 뒤 앱을 실행해, 화면이
그 서비스 이름·영향받는 기능·다음에 할 일을 말하는지 본다. 나머지 기능은 계속 쓸 수
있어야 한다.

**Acceptance Scenarios**:

1. **Given** 설치 직후 첫 실행, **When** 앱을 연다, **Then** 준비 중인 단계가 이름과 함께
   진행 표시로 보이고, 끝나기 전에는 아직 못 쓰는 기능이 눌리지 않거나 그 이유를 말한다.
2. **Given** 레거시 분석에 필요한 서비스만 못 떴다, **When** 사용자가 앱을 본다,
   **Then** 문서 업로드·설계는 정상으로 표시되고 **분석 탭만** 사용 불가와 그 이유·
   복구 방법을 보여준다.
3. **Given** 컨테이너 실행 환경(Docker) 자체가 안 떠 있다, **When** 앱을 연다,
   **Then** "무엇을 준비해야 하는가"(= 컨테이너 실행 환경 시작)를 화면에서 말하고,
   준비된 뒤 다시 시도할 수 있는 길을 준다.
4. **Given** 어떤 서비스가 응답은 하는데 실제 기능이 안 되는 상태, **When** 준비 판정을
   한다, **Then** **프로세스 존재나 포트 열림만으로 준비 완료로 치지 않는다** —
   그 서비스의 실제 동작을 확인한 결과로 판정한다.

### User Story 2 - 설치본에서 분석이 설계를 지우지 않는다 (Priority: P1)

사용자가 문서로 설계를 만들어 둔 프로젝트에서 레거시 코드 분석을 돌린다. 분석은
자기 저장 영역을 비우고 새로 쓴다. 그 영역이 설계와 같은 곳이면 설계가 사라진다.

**Why this priority**: 데이터 손실이다. 그리고 오류가 안 난다 — 분석은 "성공"으로 끝난다.

**Independent Test**: 격리된 검증 영역에 설계 데이터를 심고 분석을 돌린 뒤, 설계
데이터의 **개수가 아니라 내용**을 되읽어 그대로인지 본다. 되돌리기에 실패하면 검사도
실패한다.

**Acceptance Scenarios**:

1. **Given** 설계 데이터가 있는 프로젝트, **When** 같은 프로젝트에서 레거시 분석을
   완주한다, **Then** 설계 데이터는 내용까지 그대로이고 분석 결과는 따로 조회된다.
2. **Given** 설치본과 개발 환경, **When** 두 환경의 저장 영역 분리 설정을 대조한다,
   **Then** 두 환경이 **같은 규칙**을 따른다 (FR-028).
3. **Given** 설정이 어긋나 설계 영역과 분석 영역이 같아졌다, **When** 앱이 기동한다,
   **Then** 분석 기능을 열기 전에 **그 충돌을 감지해 막고** 사용자에게 알린다.

### User Story 3 - 껐다 켜도, OS 를 재시작해도 같게 동작한다 (Priority: P1)

사용자가 앱을 닫는다. 다시 연다. PC 를 재시작하고 다시 연다. 매번 같은 화면,
같은 데이터, 같은 속도로 들어간다.

**Why this priority**: 사내망 사용자의 일상 동작이다. 여기서 갈리면 "왜 나만 되지"가
시작된다.

**Independent Test**: 앱 정상 종료 · 강제 종료 · OS 재시작 세 경우 각각에서 다시 열어,
중복 실행된 서비스가 없고 앱이 전과 같은 서비스에 붙는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 앱을 정상 종료했다, **When** 다시 연다, **Then** 앱이 소유한 서비스가
   중복으로 뜨지 않고, 전에 쓰던 데이터가 그대로 있다.
2. **Given** 앱을 강제 종료했다, **When** 다시 연다, **Then** 남은 프로세스 때문에
   기동이 막히지 않는다 — 앱이 자기 것을 알아보고 이어받거나 정리한다.
3. **Given** OS 를 재시작했다, **When** 앱을 연다, **Then** 앱이 관리하는 서비스가
   **앱 없이 먼저 떠 있었더라도** 앱이 그것을 자기 것으로 인지하고 붙는다.
4. **Given** 이전 실행에서 쓰던 연결 정보가 지금은 다른 것이 쓰고 있다, **When** 앱이
   기동한다, **Then** 조용히 실패하지 않고 새로 확보하거나 사용자에게 무엇이 막혔는지
   말한다.
5. **Given** 사용자가 앱이 관리하는 서비스를 완전히 내리고 싶다, **When** 화면에서
   그것을 요청한다, **Then** 앱이 자기 소유의 서비스만 내리고 **사용자 데이터는
   보존한다**.

### User Story 4 - 고장 나도 작업을 잃지 않고 돌아온다 (Priority: P2)

작업 중에 서비스가 죽거나 느려진다. 화면은 무한히 기다리지 않는다. 무엇이 실패했고
어디서부터 다시 하면 되는지 말한다. 복구한 뒤 같은 작업이 두 번 반영되지 않는다.

**Why this priority**: P1 셋이 없으면 이것을 보여줄 화면 자체가 없다. 순서가 뒤다.

**Independent Test**: 작업 도중 서비스를 강제로 내리고, 화면이 유한한 시간 안에
실패를 말하는지 · 복구 후 데이터가 중복되거나 사라지지 않는지 본다.

**Acceptance Scenarios**:

1. **Given** 긴 작업(문서 인제스천·레거시 분석) 도중 서비스가 죽었다, **When** 사용자가
   화면을 본다, **Then** **성공처럼 멈추지 않고** 실패한 단계를 이름으로 말한다.
2. **Given** 서비스가 죽었다, **When** 앱이 그것을 감지한다, **Then** 스스로 되살리기를
   시도하고 그 시도와 결과를 화면에서 알 수 있다. 되살리기를 포기하는 조건이 있다.
3. **Given** 복구했다, **When** 사용자가 같은 작업을 다시 진행한다, **Then** 앞서
   완료된 부분이 중복 반영되지 않고 기존 데이터가 사라지지 않는다.
4. **Given** 빈 목록이 화면에 나왔다, **When** 사용자가 본다, **Then** **정상적인 데이터
   부재 · 처리 실패 · 조회 실패가 서로 다른 메시지로** 구분된다.

---

### User Story 5 - BPMN 을 누가 냈는지 나중에도 안다 (Priority: P2)

사용자가 문서를 넣어 업무흐름을 만든다. 내부 서비스가 냈는지, 대체 경로가 냈는지가
결과에 남는다. 앱을 다시 열어도 그 기록이 보인다.

**Why this priority**: 사내망에서 내부 서비스가 놀고 있어도 대체 경로가 결과를 내면
아무도 모른다. 결과물로는 갈리지 않는다 — 기록이 유일한 증거다.

**Independent Test**: 내부 서비스를 내린 상태와 띄운 상태로 각각 같은 문서를 넣고,
결과에 남은 출처가 갈리는지 본다. 판정은 **결과물 품질이 아니라 처리 서비스가 받은
요청**으로 한다.

**Acceptance Scenarios**:

1. **Given** 내부 서비스가 정상, **When** 문서로 업무흐름을 만든다, **Then** 결과에
   내부 서비스가 처리했다는 기록이 남고 앱을 다시 열어도 보인다.
2. **Given** 내부 서비스가 실패해 대체 경로가 돌았다, **When** 결과가 화면에 나온다,
   **Then** **성공처럼 보이지 않는다** — 대체 경로가 썼다는 것과 그 이유가 드러난다.
3. **Given** 대체 경로를 쓰지 않도록 설정했다, **When** 내부 서비스가 실패한다,
   **Then** 결과를 만들지 않고 실패로 끝난다.

---

### User Story 6 - 설치본에서 로그인하고 내 프로젝트로 들어간다 (Priority: P1)

사용자가 설치본을 열어 자기 계정으로 로그인하고, 자기 프로젝트를 골라 들어간다.
다른 사용자의 프로젝트 데이터는 보이지 않는다.

**Why this priority**: 인수조건의 화면 경로가 여기서 시작한다. 이것이 없으면 그
뒤의 모든 경로를 사람이 밟을 수 없다. 저장소를 개발 환경과 같은 구성으로 맞추기로
한 결정(FR-028)이 이 이야기를 이번 범위 안으로 끌어온다.

**Independent Test**: 설치본에서 두 사용자로 각각 로그인해, 상대 프로젝트의
데이터를 심어 두고 **그 라벨을 세어** 안 보이는지 확인한다. 빈 목록으로 판정하지
않는다 — 권한이 없어도 빈 결과가 나오기 때문이다.

**Acceptance Scenarios**:

1. **Given** 설치본, **When** 사용자가 로그인한다, **Then** 자기 프로젝트 목록이 보이고
   고를 수 있다.
2. **Given** 두 사용자의 프로젝트에 각각 데이터가 있다, **When** 한 사용자로 접속해
   조회한다, **Then** 상대 프로젝트의 데이터가 **한 건도** 나오지 않는다.
3. **Given** 로그인에 필요한 서비스가 준비되지 않았다, **When** 앱을 연다, **Then**
   빈 화면이 아니라 **무엇이 준비되지 않았는지**를 보여준다.

---

### Edge Cases

- 이미지 압축 해제 도중 디스크가 부족하면? → 실패 단계와 필요 용량을 말한다.
- 기동이 예상보다 훨씬 오래 걸리는 중인가, 멎었는가? → 둘이 화면에서 구분돼야 한다.
- 같은 PC 에서 앱을 두 번 실행하면? → 두 번째 창이 조용히 사라지지 않는다.
- 사용자가 컨테이너 실행 환경을 작업 도중에 종료하면? → 진행 중 작업의 실패와
  영향받는 기능이 화면에 나온다.
- 앱 버전과 서비스 버전 조합이 맞지 않으면? → 기동 전에 감지하고 무엇이 안 맞는지 말한다.
- 업그레이드 후 데이터를 못 읽으면? → 이전 정상 상태로 돌아갈 수 있고, 돌아간 뒤
  데이터가 온전하다.
- 사내망이라 외부를 못 부르는 상태에서 외부 의존이 남아 있으면? → 그 기능이 열리기
  전에 막히고 무엇이 필요한지 말한다.

## Requirements *(mandatory)*

### Functional Requirements

**준비 상태와 표시**

- **FR-001**: 앱은 자기가 관리하는 각 서비스의 준비 상태를 **서비스 단위로** 알아야 한다.
- **FR-002**: 준비 판정은 프로세스 존재나 연결 열림이 아니라 **그 서비스가 실제로 일을
  하는지 확인한 결과**여야 한다.
- **FR-003**: 앱은 각 서비스의 상태를 화면에 드러내야 한다 — 준비 중 · 준비됨 ·
  실패 · 앱이 관리하지 않음.
- **FR-004**: 서비스가 실패하면 화면은 **영향받는 기능**과 **사용자가 할 수 있는 복구
  동작**을 함께 보여야 한다.
- **FR-005**: 앱이 관리하는 서비스와 외부에서 제공되는 서비스를 화면에서 구분해야 한다.
- **FR-006**: 의존하는 서비스가 준비되기 전에는 그 기능을 열지 않거나, 왜 못 여는지를
  말해야 한다.

**설정 계약**

- **FR-007**: 설치본에서 설계 데이터 영역과 레거시 분석 데이터 영역은 **분리돼야** 한다.
- **FR-008**: 앱은 기동 시 그 분리가 성립하는지 확인하고, 안 되면 분석 기능을
  **열기 전에 막고** 알려야 한다.
- **FR-009**: 설치본은 개발 장비에 남아 있는 설정이나 손으로 띄운 서비스에 의존해
  동작해서는 안 된다.
- **FR-010**: 개발 환경과 설치본은 **같은 저장소 구성**을 쓴다(FR-028). 지원하는 구성이
  문서에 명시돼야 하고, 지원하지 않는 구성으로 붙으면 그것을 화면에서 알 수 있어야 한다.
- **FR-011**: 비밀정보는 배포 자산과 분리해 보관하고 화면·로그·진단 출력에 남기지
  않아야 한다.

**수명 관리**

- **FR-012**: 앱은 자기가 소유한 서비스를 **자기 것으로 식별**할 수 있어야 하고, 남의
  것을 건드려서는 안 된다.
- **FR-013**: 앱을 다시 열었을 때 이미 떠 있는 자기 소유 서비스를 **중복으로 띄우지
  않고 이어받아야** 한다.
- **FR-014**: 강제 종료 후 재실행에서 남은 프로세스 때문에 기동이 막히지 않아야 한다.
- **FR-015**: 사용자는 앱이 관리하는 서비스를 **화면에서 완전히 내릴 수 있어야** 하며,
  그때 사용자 데이터는 보존돼야 한다.
- **FR-016**: 이전 실행의 연결 정보를 그대로 쓸 수 없는 상황에서 조용히 실패하지 않고
  새로 확보하거나 사용자에게 알려야 한다.

**복구**

- **FR-017**: 앱은 자기가 관리하는 서비스의 비정상 종료를 감지해야 한다.
- **FR-018**: 앱은 되살리기를 시도하고, 시도 횟수 또는 시간 한계에 이르면 멈추고
  사용자에게 넘겨야 한다.
- **FR-019**: 화면은 무한히 기다려서는 안 된다 — 한계 시간 안에 실패로 결론내야 한다.
- **FR-020**: 복구 후 이어서 진행할 때 이미 반영된 작업이 중복 반영돼서는 안 된다.
- **FR-021**: 빈 결과는 **정상적인 데이터 부재 · 처리 실패 · 조회 실패**를 화면과 기록
  양쪽에서 구분해야 한다.

**버전과 데이터 보존**

- **FR-022**: 앱과 각 서비스의 버전 조합을 사용자와 진단 기록에서 확인할 수 있어야 한다.
- **FR-023**: 사용자 데이터는 실행 파일 교체·서비스 교체와 독립적으로 보존돼야 한다.
- **FR-024**: 업그레이드가 실패하면 데이터 호환성을 확인한 뒤 이전 정상 상태로 돌아갈
  수 있어야 한다.

**업무흐름 생성 출처**

- **FR-025**: 업무흐름 생성 결과에는 **어느 처리 서비스가 냈는지**가 결과와 함께
  보존돼야 하고, 앱을 다시 열어도 확인할 수 있어야 한다.
- **FR-026**: 대체 경로가 돌았다면 그 사실과 사유가 결과에 드러나야 하며 성공처럼
  보여서는 안 된다.
- **FR-027**: 대체 경로를 쓰지 않도록 설정할 수 있어야 하고, 그때 내부 서비스 실패는
  실패로 끝나야 한다.

### Key Entities

- **관리 대상 서비스**: 앱이 수명을 책임지는 하나의 서비스. 이름 · 준비 상태 ·
  이 서비스가 없으면 못 쓰는 기능 목록 · 소유 주체(앱/외부) · 버전.
- **런타임 상태**: 현재 실행의 전체 그림. 서비스별 상태 · 앱 버전 · 데이터 위치 ·
  업그레이드 상태.
- **데이터 영역**: 한 프로젝트의 설계 데이터와 분석 데이터가 각각 사는 곳. 둘은 겹치면
  안 된다.
- **업무흐름 생성 기록**: 결과와 함께 남는 처리 출처 · 사유 · 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 외부 인터넷이 차단된 배포 대상 환경에서 설치본을 설치해 실행했을 때,
  문서 업로드 → 업무흐름 생성 → 레거시 분석·탐색 → 이벤트 스토밍 생성까지
  **사람이 화면에서 밟는 경로로** 완주한다.
- **SC-002**: 관리 대상 서비스 각각을 하나씩 못 뜨게 했을 때, **모든 경우에** 화면이
  그 서비스 이름과 영향받는 기능과 복구 방법을 보여준다 (누락 0건).
- **SC-003**: 설계 데이터가 있는 프로젝트에서 레거시 분석을 완주한 뒤, 설계 데이터의
  **내용이** 분석 전과 동일하다.
- **SC-004**: 정상 종료 · 강제 종료 · OS 재시작 각각 뒤의 재실행에서 중복 실행된
  관리 대상 서비스가 0개이고, 앱이 전과 같은 데이터에 붙는다.
- **SC-005**: 작업 도중 서비스를 강제로 내렸을 때 화면이 정해진 한계 시간 안에 실패를
  말한다 — 무한 대기 0건.
- **SC-006**: 복구 후 이어서 진행했을 때 중복 반영된 항목 0건, 사라진 항목 0건.
- **SC-007**: 내부 업무흐름 서비스를 내린 상태와 띄운 상태에서 같은 문서를 넣었을 때,
  결과에 남은 출처가 서로 다르다. 판정 근거는 **처리 서비스가 받은 요청 수**다.
- **SC-008**: 이 스펙에 딸린 모든 검사는 **격리된 검증 환경에서 결함을 심었을 때
  실패하고, 결함을 제거하면 다시 통과한다.**
- **SC-009**: 실행하지 못한 환경과 경로는 **미검증으로 기록**된다 — "안 된다"와 "모른다"가
  구분된다.
- **SC-010**: 설치본에서 서로 다른 두 사용자로 로그인해 각자의 프로젝트를 열었을 때,
  상대의 데이터가 **한 건도** 보이지 않는다. 판정은 빈 목록이 아니라 심어 둔 데이터를
  세서 한다.
- **SC-011**: 저장소 회귀 검사가 **설치본 구성에서** 통과한다 — 개발 환경 통과를
  설치본 통과로 치지 않는다.

## Assumptions

- 배포 대상 환경에는 컨테이너 실행 환경이 **사용자 책임으로** 미리 설치돼 있다.
  앱은 그것을 설치하지 않고, 없으면 무엇을 준비해야 하는지 알린다.
- 사내 모델 서비스처럼 앱 밖에서 제공되는 의존은 앱이 관리하지 않는다. 앱은 그 연결
  조건과 상태만 드러낸다.
- 릴리스 빌드 자체(이미지 묶음 생성 · 설치본 패키징 · 환경 키 주입)는 `robo-workspace`
  소유이며 이 스펙의 비목표다. 이 스펙은 **만들어진 설치본이 어떻게 행동해야 하는가**를
  정한다.
- SSO/기업 인증 배선은 이 스펙의 비목표다 (`ENT-AUTH-001`).
- **모델 제공자는 현재 OpenAI 이고, 이후 P-GPT(고객 사내 OpenAI 호환)로 바뀐다**
  (2026-09-17 사용자 확인). 이 스펙은 특정 제공자를 전제하지 않고, **제공자 연결이
  안 될 때 그것이 드러나는가**만 요구한다(FR-002 · FR-004).
- 릴리스 환경 템플릿에 **개발사 내부 모델 주소가 남아 있는 상태**가 실측됐다.
  그 정리는 이 스펙의 선행 과제로 둔다(계획 단계 태스크).
- `054-docker-managed-electron-distribution` 의 배포 구성 계약은 전제로 삼는다.
  이 스펙은 그 위의 감독·복구·표시를 더한다.
- 054 는 "앱 종료 시 서비스는 warm 으로 남긴다"를 의도한 설계로 정했다. 이 스펙은
  그것을 뒤집지 않고, **명시적으로 내리는 길**과 **다시 붙는 길**을 요구한다.
- 강제 이어받기(다른 사용자의 선점 뺏기)는 `057` 의 명시적 비목표이며 여기서도 아니다.

## 정해진 것 (2026-09-17 사용자 결정)

### 저장소 구성 — Ontological 로 맞춘다

설치본의 graph 저장소를 개발 환경과 같은 구성으로 옮긴다. 그 결과 **사용자·프로젝트
관리가 설치본에 들어온다** — 사용자 = 저장소 role, 프로젝트 = graph, 공유 = 권한 부여.

- **FR-028**: 설치본의 graph 저장소는 개발 환경과 **같은 엔진·같은 분리 규칙**을 써야
  한다. 두 환경에서 같은 질의가 같은 결과를 내야 한다.
- **FR-029**: 설치본에서 사용자는 **로그인하고 자기 프로젝트를 골라** 들어갈 수 있어야
  한다. 다른 사용자의 프로젝트 데이터는 보이지 않아야 한다.
- **FR-030**: 기존 설치본 구성(다른 엔진)에 남은 사용자 데이터가 있다면, **옮길 수
  있거나 옮길 수 없음을 기동 시 알려야** 한다 — 조용히 빈 화면이 되어서는 안 된다.
- **FR-031**: 저장소 엔진의 **조용한 오답**을 막는 회귀 검사가 설치본 구성에서도
  돌아야 한다. 개발 환경에서 통과한 것을 설치본의 통과로 간주하지 않는다.
- **FR-032**: 권한이 좁혀진 사용자로 접속했을 때 **남의 graph 데이터가 새지 않아야**
  한다. 빈 graph 로는 이것을 판정하지 않는다 — 데이터를 심고 센다.

### 검증 환경 — Windows 설치본으로 잰다

Windows 장비가 있다. 인수조건의 "배포 대상 환경에서 실제 설치본을 오프라인으로"를
이번 회차에 실제로 수행한다.

- **FR-033**: 이 스펙의 인수 판정은 **개발 서버가 준비된 장비가 아니라, 릴리스로
  만든 설치본을 Windows 에 설치하고 외부 인터넷을 차단한 상태에서** 수행한다.
- **FR-034**: mac 패키징 경로는 이 스펙의 비목표이며 **미검증으로 명시**한다.
- **FR-035**: 설치 전제조건(컨테이너 실행 환경, 사내 모델 서비스 연결 등)은 문서에
  기록하고, 누락됐을 때 **화면에서 무엇을 준비해야 하는지** 알 수 있어야 한다.
- **FR-036**: 배포 자산(추적되는 템플릿 포함)에 **개발사 내부 서비스 주소·키가 남아
  있어서는 안 된다.** 값이 채워져 있다는 것과 맞는 값이라는 것은 다르다 — 릴리스
  검사는 전자만 본다.
