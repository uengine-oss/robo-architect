# Feature Specification: 완성 설계 Import (Design tab Finished-Design Import)

**Feature Branch**: `044-design-import`

**Created**: 2026-06-29

**Status**: Draft

**Input**: User description: "완성 설계 import 는 디자인 탭에 넣는게 좋겠어. /speckit-specify 를 통해서 해당 기능을 명세하고 구현체를 담아줘" — Design 탭에서 이미 완성된 이벤트스토밍 설계 문서를 LLM 재분해 없이 결정론적으로 그래프에 그대로 적재해 즉시 렌더링.

## Summary

아키텍트가 **이미 완성된 이벤트스토밍 설계 문서**(Bounded Context별 Aggregate·Command·Event·Policy·ReadModel·Invariant가 표로 정리된 마크다운; 예: TM Forum ODA 표준 컴포넌트 캔버스)를 **Design 탭에서 직접 업로드**하면, 시스템이 이를 **LLM 재해석 없이 결정론적으로** 파싱하여 도메인 모델 그래프에 **그대로(faithfully)** 적재하고 Design 탭(빅픽처 타임라인/캔버스)에 즉시 렌더링한다.

기존 문서 업로드(Stories 탭, LLM 인제스천)는 자연어 요구사항을 **재분해**하는 single-model 파이프라인이라 (1) 완성된 설계를 넣으면 사용자 스토리가 추출되지 않아 모델이 만들어지지 않고, (2) 그래프 전체를 덮어쓴다. 본 기능은 그 한계를 메우는 **별도 진입점**으로, 충실도 보존과 Design 탭 직접 진입을 핵심 가치로 한다. 적재 전 **미리보기(개수·경고)** 와 **사람 확정 게이트**를 두고, **교체/병합** 모드를 선택할 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 완성 설계를 Design 탭에서 가져오기 (Priority: P1)

아키텍트가 Design 탭에서 "설계 가져오기(Import)" 진입점을 열어 완성된 이벤트스토밍 설계 문서를 업로드한다. 시스템은 문서를 결정론적으로 파싱해 Bounded Context와 그 안의 Aggregate·Command·Event·Policy·ReadModel·Invariant, 그리고 컨텍스트 간 반응(이벤트→정책→명령) 연결을 추출하고, 적재 시 생길 노드/관계 개수와 경고를 **미리보기**로 보여준다. 아키텍트가 확정하면 모델이 그래프에 적재되고 Design 탭이 자동으로 새로고침되어 빅픽처 타임라인/캔버스에 설계가 그대로 나타난다.

**Why this priority**: 이 스토리가 없으면 기능 자체가 존재하지 않는다. 완성 설계를 충실히 적재해 Design 탭에서 보는 것이 본 기능의 근본 가치다.

**Independent Test**: 완성 설계 마크다운 1건을 업로드 → 미리보기에 BC/Aggregate/Command/Event/Policy 개수가 표시 → 확정 → Design 탭에 동일 구조가 렌더링되는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** Design 탭에 "설계 가져오기" 진입점이 있을 때, **When** 아키텍트가 완성 설계 문서를 업로드하면, **Then** 시스템은 적재될 BC·Aggregate·Command·Event·Policy·ReadModel·Invariant 개수와 경고 목록을 미리보기로 제시한다.
2. **Given** 미리보기가 제시되었을 때, **When** 아키텍트가 적재를 확정하면, **Then** 모델이 그래프에 적재되고 Design 탭이 자동 새로고침되어 BC 스윔레인과 이벤트, 컨텍스트 간 연결이 표시된다.
3. **Given** 동일 문서를 두 번 적재했을 때(같은 입력), **When** 결과 그래프를 비교하면, **Then** 노드/관계 구성이 동일하다(결정론적).
4. **Given** 문서의 어떤 명령이 어떤 이벤트를 발행하는지 명시되어 있을 때, **When** 적재가 끝나면, **Then** 각 Event는 발행 Command에, 각 Command는 Aggregate에, 각 Aggregate는 BC에 연결되어 타임라인에 노출된다.

---

### User Story 2 - 교체/병합 모드 선택 (Priority: P2)

아키텍트는 가져오기 시 **교체(기존 모델을 비우고 이 설계로 대체)** 또는 **병합(기존 모델 위에 추가)** 중 하나를 선택한다. 교체는 단일 모델 워크플로우(한 문서 = 활성 모델)에 맞고, 병합은 여러 설계 조각을 누적할 때 쓴다.

**Why this priority**: 단일 모델만 지원하면 기존 작업을 의도치 않게 덮어쓸 위험이 있다. 모드 선택은 안전과 누적 시나리오를 모두 보장하지만, P1 적재가 먼저 가치가 있으므로 P2.

**Independent Test**: 기존 모델이 있는 상태에서 교체로 적재 → 기존이 사라지고 새 설계만 남음. 병합으로 적재 → 기존 + 새 설계가 공존. 두 경우 모두 미리보기에 모드 영향이 표시되는 것으로 검증.

**Acceptance Scenarios**:

1. **Given** 그래프에 기존 모델이 있을 때, **When** 아키텍트가 **교체** 모드로 적재를 확정하면, **Then** 기존 이벤트스토밍 모델이 제거되고 새 설계만 남는다.
2. **Given** 그래프에 기존 모델이 있을 때, **When** 아키텍트가 **병합** 모드로 적재를 확정하면, **Then** 기존 모델은 유지되고 새 설계가 추가된다.
3. **Given** 교체 모드가 선택되었을 때, **When** 미리보기를 보면, **Then** "기존 N개 BC가 제거됨" 같은 영향이 명시된다.

---

### User Story 3 - 불완전/오류 입력의 안전한 처리 (Priority: P3)

문서에 형식 오류나 매핑되지 않는 참조(예: 존재하지 않는 Command를 호출하는 Policy, 발행 Command가 불명확한 Event)가 있어도, 시스템은 전체를 거부하지 않고 **적재 가능한 부분은 적재**하며 문제 항목을 **경고**로 표면화한다.

**Why this priority**: 견고성은 중요하지만 정상 경로(P1) 이후의 품질이므로 P3.

**Independent Test**: 일부러 끊어진 참조를 포함한 문서를 업로드 → 미리보기/결과에 경고가 표시되고, 정상 부분은 그래프에 들어가는 것으로 검증.

**Acceptance Scenarios**:

1. **Given** Policy가 존재하지 않는 Command를 가리킬 때, **When** 적재하면, **Then** 그 연결은 건너뛰고 경고에 기록되며 나머지는 적재된다.
2. **Given** 표 형식이 부분적으로 깨졌을 때, **When** 파싱하면, **Then** 인식 가능한 BC/요소는 적재되고 인식 실패 구간은 경고로 보고된다.
3. **Given** 빈 문서나 인식 가능한 설계 요소가 0개일 때, **When** 업로드하면, **Then** 시스템은 적재하지 않고 "인식된 설계 요소 없음"을 명확히 알린다.

---

### Edge Cases

- **중복 이름**: 같은 BC 안에 동일 이름 Aggregate/Command가 두 번 나오면 하나로 합치고 경고한다.
- **컨텍스트 간 연결**: 한 BC의 이벤트가 다른 BC의 정책을 트리거하는 연결(사가 스파인)은 양쪽 BC가 모두 인식된 경우에만 그려지고, 한쪽이 없으면 경고한다.
- **대용량 문서**: 다수 BC(수십 개)·수백 요소 문서도 미리보기와 적재가 완료된다.
- **기존 업로드 무회귀**: 본 기능 추가가 Stories 탭의 LLM 문서 업로드 동작을 바꾸지 않는다.
- **부분 확정 취소**: 미리보기 후 적재를 취소하면 그래프는 변경되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 **Design 탭**에 완성 설계 문서를 업로드하는 진입점을 제공해야 한다.
- **FR-002**: 시스템은 업로드된 설계 문서를 **LLM 없이 결정론적으로** 파싱해 Bounded Context와 그 하위 Aggregate·Command·Event·Policy·ReadModel·Invariant, 그리고 명령→이벤트·이벤트→정책→명령(컨텍스트 간 반응) 관계를 추출해야 한다.
- **FR-003**: 동일 입력 문서에 대해 적재 결과 그래프(노드/관계 구성)는 **항상 동일**해야 한다(결정론).
- **FR-004**: 시스템은 적재 **전에** 생성될 BC·Aggregate·Command·Event·Policy·ReadModel·Invariant 개수와 경고 목록을 **미리보기**로 제시하고, 아키텍트의 **명시적 확정** 후에만 그래프를 변경해야 한다.
- **FR-005**: 시스템은 적재 모드로 **교체(기존 모델 제거 후 대체)** 와 **병합(기존 모델에 추가)** 을 제공하고, 선택된 모드의 영향을 미리보기에 반영해야 한다.
- **FR-006**: 적재된 모델은 Design 탭의 기존 조회 경로가 요구하는 구조 — 각 Event는 발행 Command에, 각 Command는 Aggregate에, 각 Aggregate는 BC에 연결되고, 컨텍스트 간 반응은 이벤트→정책→명령으로 연결 — 로 생성되어 **추가 변환 없이 즉시 렌더링**되어야 한다.
- **FR-007**: 적재 완료 후 Design 탭은 **자동으로 새로고침**되어 가져온 설계를 표시해야 한다.
- **FR-008**: 형식 오류·매핑 불가 참조가 있어도 시스템은 전체를 거부하지 않고 **적재 가능한 부분을 적재**하며 문제를 **경고**로 표면화해야 한다.
- **FR-009**: 인식 가능한 설계 요소가 0개이면 시스템은 그래프를 변경하지 않고 그 사실을 명확히 알려야 한다.
- **FR-010**: 본 기능 추가는 기존 문서 업로드(LLM 인제스천) 및 Design 탭의 기존 동작에 **회귀를 일으키지 않아야** 한다.
- **FR-011**: 적재된 노드는 본 가져오기에서 비롯되었음을 식별할 수 있는 **출처 표시**를 가져, 추후 식별·정리가 가능해야 한다.

### Key Entities

- **Finished Design Document**: 완성된 이벤트스토밍 설계를 담은 업로드 문서. BC별 요소 표를 포함.
- **Bounded Context**: 설계의 최상위 컨테이너. 이름·표시명·설명(도메인/표준 매핑 등)을 가진다.
- **Aggregate**: BC에 속하는 일관성 경계. 선택적으로 Invariant를 가진다.
- **Command**: Aggregate에 대한 행위. 행위자(actor)를 가지며 하나 이상의 Event를 발행할 수 있다.
- **Event**: 과거형 도메인 사실. 발행 Command와 표시명을 가진다.
- **Policy**: BC에 속하는 반응 규칙. 트리거 Event와 호출 Command(컨텍스트 간 스파인)를 참조한다.
- **ReadModel**: BC의 조회 모델.
- **Invariant**: Aggregate의 불변식.
- **Import Preview**: 적재 전 개수·경고·모드 영향 요약.
- **Import Result**: 적재된 노드/관계 개수와 경고를 포함한 결과.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 아키텍트는 완성 설계 문서를 Design 탭에서 **한 번의 업로드 + 한 번의 확정**으로 그래프에 적재할 수 있다.
- **SC-002**: 적재 후 문서에 기술된 모든 Bounded Context가 Design 탭에 표시된다(누락 0건, 인식 실패는 경고로 보고).
- **SC-003**: 동일 문서를 두 번 적재했을 때 결과 그래프 구성이 100% 동일하다(결정론).
- **SC-004**: 문서에 명시된 명령→이벤트·이벤트→정책→명령 연결의 95% 이상이 그래프에 반영된다(나머지는 경고로 설명).
- **SC-005**: 본 기능 적재 경로는 LLM을 호출하지 않으며, 일반 규모 문서(수십 BC)의 미리보기와 적재가 수 초 내에 완료된다.
- **SC-006**: 본 기능 추가 후에도 기존 문서 업로드(LLM 인제스천)와 Design 탭 조회의 기존 결과가 변하지 않는다.

## Assumptions

- 입력 문서는 BC별로 요소(Aggregate/Command/Event/Policy/ReadModel/Invariant)가 표/구조로 정리된 **완성 설계**다. 자유 산문 요구사항은 본 기능의 대상이 아니다(그쪽은 기존 LLM 인제스천).
- "Design 탭"은 도메인 모델을 빅픽처/캔버스로 보여주는 기존 화면을 가리킨다.
- 표시 언어 등 사용자 대면 텍스트는 사용자 언어 설정(BCP-47, 기본=브라우저 로케일) 정책을 따른다.
- 단일 모델 의미론(한 활성 모델)이 기본 전제이며, 교체가 기본 모드·병합이 옵션이다.

## Dependencies

- Design 탭의 기존 도메인 모델 조회·렌더링 경로(빅픽처 타임라인/캔버스).
- 기존 도메인 모델 그래프 스키마(BC·Aggregate·Command·Event·Policy·ReadModel·Invariant 및 그 관계).

## Out of Scope

- LLM 기반 재분해·자연어 요구사항 추출(기존 문서 업로드의 영역).
- ODA 표준 적합성 검증/분류(피처 043).
- 코드 생성·구현 산출물.
- 설계 문서 포맷 자체의 표준화/버전 관리.
